\chapter{LLM-Driven Drone Supervision via Tool-Call Execution}
\label{chap:3rd chap}

% ==================================================================
\section{Introduction}
\label{sec:ch3_intro}
% ==================================================================

Chapter~\ref{chap:2nd chap} demonstrated that a multimodal LLM can interpret a 320$\times$240 camera frame and suggest a pilot action with 97.5\% action safety --- but the output remained advisory: a human pilot still had to act on the recommendation.
This chapter asks a harder question: can the LLM \emph{directly command} the drone, translating a single natural-language sentence such as ``take off and hover at one metre'' into the precise sequence of API calls that arms the motors, calibrates hover throttle, engages altitude hold, and waits for steady state, with no human reformulation at any step?

Enabling this requires three conditions to hold simultaneously.
First, the physics simulator must accurately reproduce the real drone's dynamics, so that all LLM command experiments are valid proxies for hardware before any live flight is run.
Second, the PID+EKF inner controller must itself meet performance specifications, since LLM-issued setpoints are only as good as the execution substrate that converts them to motor commands.
Third, the LLM must correctly parse diverse natural-language phrasings, maintain flight state across conversational turns, self-diagnose control faults, and respond to emergency overrides --- all without receiving step-by-step programmatic instructions.

These three conditions define the three research questions answered in this chapter:
\begin{enumerate}
  \item Does the physics simulator accurately reproduce the real drone's dynamics so that all LLM command experiments are valid proxies for hardware?
  \item Does the PID+EKF controller meet performance specifications for altitude hold, position hold, and attitude control, establishing a reliable execution substrate?
  \item Can the LLM correctly interpret and execute natural-language commands across eight scenarios spanning explicit targets, paraphrases, ambiguous instructions, multi-turn missions, mid-mission re-targeting, PID self-tuning, mission planning, and safety override?
\end{enumerate}

A-series experiments (\S\ref{sec:ch3_aseries}) validate six physics sub-models against analytical solutions and peer-reviewed empirical data.
B-series (\S\ref{sec:ch3_bseries}) characterise PID+EKF performance across five flight scenarios.
C-series (\S\ref{sec:ch3_cseries}) test the full LLM supervisor across eight command scenarios of increasing complexity, evaluated under the standardised HELM protocol~\cite{liang2023helm}.

\section{System Design}
\label{sec:ch3_proposed}
% ==================================================================

\subsection{Architecture: Timescale-Separated Supervision}
\label{sec:ch3_proposed_arch}

The central design principle is timescale separation: safety-critical attitude control runs at kilohertz rates entirely on the microcontroller, while the LLM supervisor operates at sub-hertz rates on the host computer and is never on the critical latency path.
This separation ensures that LLM inference latency (0.5--2~s per round-trip) cannot destabilise flight even if the model stalls or produces an erroneous output.

Three timescale-matched layers implement this separation (Figure~\ref{fig:ch3_architecture}):

\begin{description}
  \item[Inner loop --- PID + EKF (4~kHz):]
    Madgwick attitude filter~\cite{madgwick2010filter} running at 200~Hz, 9-state EKF~\cite{kalman1960filter, welch1995kalman} at 250~Hz, and cascaded PID at 4,000~Hz executing on the ESP32-S3 microcontroller.
    This layer never queries or waits for the LLM; it runs continuously whether or not a command is in flight.
  \item[Middle layer --- Tool server ($\sim$10~Hz):]
    \texttt{keyboard\_server.py} translates JSON tool calls into WebSocket messages to the ESP32.
    Maintains a live flight-state model and enforces hard safety guardrails: altitude is clamped to $[0.2,\,2.5]$~m; roll and pitch are bounded below $20°$; disarm state is checked before any armed-mode tool is executed.
    Guardrail violations return a structured JSON error to the LLM, prompting a corrected retry rather than aborting the session.
  \item[Outer loop --- LLM supervisor (0.5--2~Hz):]
    The LLM receives a natural-language command and enters a ReAct~\cite{yao2022react} reason--act--observe loop.
    Each iteration: (1) reason about intent given the current telemetry and conversation history, (2) call one tool from the exposed API, (3) observe the tool response, and (4) decide the next action.
    The loop terminates when the mission objective is verifiably met (e.g.\ altitude within tolerance) or a terminal state (land, disarm) is reached.
\end{description}

\subsection{Tool API}
\label{sec:ch3_proposed_tools}

The tool namespace exposes 13 typed functions (Table~\ref{tab:ch3_tools}).
Guardrail-protected tools ($\dagger$) validate their parameters before execution and return a structured JSON error on out-of-range values; the LLM must retry with corrected arguments.
This design keeps safety enforcement in the deterministic tool server rather than relying on the LLM to self-constrain, consistent with the SayPlan and SayCan safety-grounding principle~\cite{ahn2022saycan}.

\section{Experimental Setup}
\label{sec:ch3_setup}
% ==================================================================

\subsection{Simulator}
\label{sec:ch3_setup_sim}

The physics simulator \texttt{drone\_sim.py} follows the sim-to-real validation methodology of Forster \textit{et~al.}~\cite{forster2015crazyflie}: each sub-model is validated independently against an analytical or empirical reference before the composite simulator is used for experiment execution.
Six sub-models are implemented (Table~\ref{tab:ch3_a_summary}):
\begin{enumerate}
  \item \textbf{Rigid body dynamics:} 4th-order Euler integration, $\Delta t=0.001$~s.
  \item \textbf{Aerodynamic drag:} viscous drag coefficient $k_D=0.02$~N$\cdot$s/m.
  \item \textbf{Ground effect:} He 2019 thrust multiplier model~\cite{he2019groundeffect}; classical Cheeseman--Bennett bound used as a validation envelope.
  \item \textbf{Motor dynamics:} first-order lag with time constant $\tau_m=30$~ms~\cite{bangura2012thrustcontrol, faessler2018differential}.
  \item \textbf{Battery discharge:} Thevenin equivalent circuit, $R_i=0.05~\Omega$, modelling voltage sag and PWM compensation~\cite{morbidi2018power, sotogarcia2023battery}.
  \item \textbf{Attitude estimation:} Madgwick filter~\cite{madgwick2010filter} fused with a 9-state Kalman EKF~\cite{kalman1960filter, welch1995kalman}.
\end{enumerate}

\subsection{Hardware Platform}
\label{sec:ch3_setup_hw}

The physical platform is a custom 50~g indoor drone built around an ESP32-S3-Sense microcontroller.
Sensing: VL53L0X Time-of-Flight altitude sensor ($\pm$2~mm resolution), MPU-6050 six-axis IMU, and optical flow module for lateral position estimation~\cite{grzonka2012indoor}.
Firmware implements a cascaded PID altitude hold~\cite{bouabdallah2004pid, narkhede2021althold}: outer altitude loop ($K_p=1.6$, $K_i=0.5$) produces a throttle correction that is fed to the inner throttle loop ($K_p=0.70$, $K_i=0.30$, anti-windup clamp $\pm$50~PWM).
Position hold uses a lateral velocity integrator ($K_p=1.2$)~\cite{chadha2023poshold}, maintaining decoupled $z$ and $xy$ control channels.

\subsection{LLM Models and Evaluation Protocol}
\label{sec:ch3_setup_eval}

All C-series experiments use Claude~3 Sonnet as the primary model, with multi-model comparisons (GPT-4o, Gemini~2.5-Flash, GPT-4o-mini) for selected scenarios.
Each run is logged via the shared \texttt{c\_series\_agent.py} scaffold, recording every tool call, LLM response, elapsed time, token count, and telemetry snapshot.
Evaluation follows the HELM~\cite{liang2023helm} protocol: five independent runs per scenario, metrics reported as mean $\pm$ 95\% CI, pass criteria pre-defined before data collection.

% ------------------------------------------------------------------
\subsection{B4 --- Wind Disturbance Rejection}
\label{sec:ch3_b4}
% ------------------------------------------------------------------

A constant 0.02~N horizontal wind force is applied while hovering at 1.0~m with both altitude and position hold active.
This models a mild indoor air current from an HVAC vent or doorway.
Steady-state (SS) XY and Z RMSE are computed over 30~s of simulated flight after the wind onset transient has decayed.

Wind rejection performance is a critical validation of the coupled altitude--position hold architecture: if lateral drag couples into the thrust axis, altitude will drift under wind~\cite{wang2019windpid, dydek2013adaptive}.

SS XY RMSE: 9.21~cm (spec $\leq$15~cm). SS Z RMSE: 0.30~cm (spec $\leq$2~cm).
Both channels remain well within specification simultaneously, confirming that the $z$--$xy$ decoupling holds under sustained wind loading.
The 9.21~cm lateral offset represents the steady-state equilibrium point where the position-hold restoring force balances the applied wind force; oscillation around this point is $<$1~cm peak-to-peak.

% ------------------------------------------------------------------
\subsection{B5 --- Battery Discharge Profile}
\label{sec:ch3_b5}
% ------------------------------------------------------------------

Hover throttle PWM is logged over a full simulated discharge from 100\% to 10\% SOC.
The altitude-hold integral autonomously compensates for falling cell voltage across the full nominal range ($>$40\% SOC), increasing hover PWM by $\Delta\text{PW}=238$.
Below $\sim$40\% SOC (cell voltage $<$3.5~V), voltage sag saturates the throttle authority margin, and the altitude-hold loop can no longer maintain the target altitude.
This establishes the $\geq$40\% SOC production constraint used in all C-series experiments.

All three research questions are answered affirmatively.

The physics simulator faithfully reproduces the real drone's dynamics within the certified indoor hover envelope, validating six sub-models against analytical solutions and peer-reviewed empirical data~\cite{forster2015crazyflie}.
Ground effect is negligible above $z=0.5$~m~\cite{cheeseman1955groundeffect, li2015groundeffect, kan2019groundeffect}; motor lag is captured within 9\% of firmware telemetry; battery-induced PWM drift matches the Thevenin model within 2~PWM across the nominal SOC range.

The PID+EKF controller meets all design specifications: altitude hold with $\leq$7\% overshoot and $\leq$0.71~cm SS RMSE~\cite{teppagarran2013althold}, position hold disturbance recovery in 1.79~s, and wind rejection at 9.21~cm XY RMSE with full $z$--$xy$ decoupling~\cite{wang2019windpid, dydek2013adaptive}.

The 26.7$\times$ altitude-tracking improvement over open-loop scripted control quantifies the value of the LLM correctly enabling feedback control.
These capabilities provide the command and execution substrate for the unified agentic patrol system in Chapter~\ref{chap:4th chap}.
